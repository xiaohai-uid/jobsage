# Feature Specification: Engine Core — P0 求职引擎与 CLI 验证（001-engine-core）

**Feature Branch**: `001-engine-core`

**Created**: 2026-08-25

**Status**: Draft

**Input**: 用户描述：把上游 ai-job-search 的核心求职工作流（档案 → 岗位匹配评估 → 简历/求职信定制草稿）移植为可独立测试的核心引擎，以 CLI 端到端验证跑通；这是 JobSage（谋职）产品的 P0 地基。所有产物仅为草稿、全部本地处理、用户自带模型密钥。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 求职者从零到第一份岗位评估报告 (Priority: P1)

一位求职者在本机完成初始化：录入自己的职业档案（教育、经历、技能、代表性成果、写作风格样本），然后粘贴一段职位描述（JD）。系统给出结构化的匹配评估报告：总体建议（值得投/谨慎/不建议）、分维度评分、优势清单、差距清单（诚实标注、不虚构）、以及下一步建议。

**Why this priority**: 这是产品价值主张的根——"先筛后投"。没有评估报告，后续的定制简历无从谈起；它独立交付了"帮你想"的核心价值。

**Independent Test**: 给定一份样例档案和样例 JD，运行一次评估命令，能得到包含评分、优势、差距、建议四要素的报告文件。

**Acceptance Scenarios**:

1. **Given** 已初始化的候选人档案, **When** 提交一段 JD 文本并请求评估, **Then** 生成的报告包含总体建议、各维度评分（含依据）、优势列表、差距列表，且差距项不包含档案中不存在的技能
2. **Given** 一段与档案明显不匹配的 JD, **When** 请求评估, **Then** 报告如实给出低分与"不建议投递"结论，而非迎合性高分
3. **Given** 无网络或未配置模型密钥, **When** 运行评估, **Then** 系统给出明确的配置指引错误信息，不崩溃、不留半成品文件

### User Story 2 - 一键生成定制简历与求职信草稿 (Priority: P1)

基于已完成的评估，求职者请求生成针对该 JD 定制的简历草稿与求职信草稿。简历按相关性加权裁剪自其真实档案（绝不虚构经历）；求职信采用面向未来的写法框架。两份产物均带有"AI 协助准备"声明选项，且明确标记为草稿。

**Why this priority**: 这是上游项目被验证的核心能力（69 申请→20 初面），也是与"海投工具"划清界限的证明点——每份产出都是深度定制的。

**Independent Test**: 对同一档案+两个不同 JD 各生成一套草稿，两套内容在重点排序与关键词覆盖上明显不同，且所有事实性陈述都能在档案中找到出处。

**Acceptance Scenarios**:

1. **Given** 已有评估报告的 JD, **When** 请求生成简历草稿, **Then** 草稿中的每条经历/技能均可在档案中追溯，无新增虚构条目
2. **Given** 简历草稿超过目标篇幅, **When** 系统裁剪, **Then** 按"与 JD 相关性 × 独特性 × 是否被求职信引用"加权保留高价值条目（对齐上游裁剪规则）
3. **Given** 任意生成的草稿, **When** 用户查看元数据, **Then** 可见 draft 状态标记与可选的 AI 协助声明文本

### User Story 3 - 双角色评审修订流水线 (Priority: P2)

草稿初稿完成后，系统以独立评审视角（新上下文、模拟招聘方+公司研究视角）批评初稿：漏掉的关键词、薄弱的表述、泛化语言；随后据批评意见修订出终稿。评审意见与修订记录留档可查。

**Why this priority**: drafter-reviewer 是上游质量优势的来源，但它建立在 Story 1/2 之上；缺了它产品仍可用，只是质量下降。

**Independent Test**: 对同一初稿运行评审+修订流程，终稿相对初稿有可见的具体改进（如补充被点评缺失的关键词），且评审意见文件存在。

**Acceptance Scenarios**:

1. **Given** 一份初稿, **When** 运行评审阶段, **Then** 产出结构化批评意见（按维度列出问题与修改建议）
2. **Given** 批评意见, **When** 运行修订阶段, **Then** 终稿针对每条意见作出回应或说明为何不改；全过程记录留档

### User Story 4 - PDF 导出 (Priority: P2)

用户将定稿的简历/求职信导出为排版稳定的 PDF 文件（版式由模板约定，渲染机制在计划阶段确定），且文件文本层可被机器解析（ATS 友好）；导出是显式的用户动作。

**Why this priority**: 投递动作发生在招聘平台，PDF 是最终交付物形态；但 CLI 验证阶段 markdown 已可评审，PDF 是通往真实使用的必要一步而非价值本身。

**Independent Test**: 导出的 PDF 能被文本提取工具读出姓名与联系方式等字面文本，无乱码字形。

**Acceptance Scenarios**:

1. **Given** 一份终稿, **When** 用户执行导出, **Then** 本地生成 PDF 文件，版式完整、页数符合模板约定
2. **Given** 导出的 PDF, **When** 用文本提取器解析, **Then** 联系方式等关键信息以可复制文本形式存在（非图形/乱码）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-1** 候选人档案管理：支持从结构化本地文件创建与编辑候选人档案，涵盖教育、工作经历、技能、代表性成果、作品集链接、写作风格样本；档案格式对人类可直接阅读编辑
- **FR-2** JD 录入：通过用户主动粘贴/导入文本文件的方式录入职位描述；P0 不实现任何招聘平台的自动抓取或登录
- **FR-3** 匹配评估：输出总体建议、多维度评分（每维含依据说明）、优势、差距、后续行动建议；评分框架语义对齐上游 fit framework（五维）
- **FR-4** 简历定制草稿：以相关性加权裁剪规则从真实档案生成；目标默认两页以内；禁止虚构——每条陈述须可追溯到档案来源
- **FR-5** 求职信草稿：一页篇幅，面向未来框架（对齐上游 cover letter 风格规则），引用档案中的真实证据
- **FR-6** 评审修订流水线：评审阶段使用独立上下文，输出结构化批评；修订阶段逐条回应；全程留痕（初稿→批评→终稿）
- **FR-7** AI 协助披露：每份产物支持附带标准化的"本材料由 AI 协助准备"声明（内容可由用户编辑）
- **FR-8** 人审边界（合规）：引擎在架构上不具备任何发送/提交/发布能力；一切产物状态为 draft；导出（含 PDF）必须是显式触发的用户动作并在记录中留痕
- **FR-9** 本地数据平面：档案、JD、草稿、报告、记录全部写入本机工作区目录；除用户配置的模型推理调用外无任何网络上传
- **FR-10** 模型接入：经统一的提供方接口接入 LLM；密钥仅从用户本地环境变量或本地配置文件读取；至少内置一个默认提供方适配，并可替换（含境内模型以便中国版使用）
- **FR-11** CLI 完整流程：提供初始化档案、评估、生成草稿、评审修订、导出五个子命令，JSON 与人类可读双输出模式，退出码语义化
- **FR-12** 上游合规分发：分发物包含上游 MIT 许可证版权声明与 NOTICE 署名文件
- **FR-13** 测试门禁：核心域逻辑测试先行；每个提供方/渲染器端口有契约测试；人审确认路径有专项测试证明"未经确认不可外发"

### Key Entities

- **CandidateProfile（候选人档案）**: 基本信息、教育、经历条目（含时间/组织/成果证据）、技能、作品集链接、写作风格样本；唯一事实源
- **JobPosting（职位描述）**: 来源标记（用户粘贴）、原文全文、结构化提取字段（职位名、要求、关键词）
- **FitEvaluation（匹配评估）**: 总体建议、维度评分及依据、优势、差距、建议动作；关联 profile 与 posting 版本
- **ApplicationDraftSet（申请草稿集）**: resumeDraft、coverLetterDraft、reviewNotes、revisionHistory、disclosure、status(恒为 draft)
- **ProviderConfig（模型配置）**: 提供方标识、模型名、密钥引用（环境变量名而非明文）

### Assumptions

- P0 为单用户本机场景，无账号体系、无并发
- 引擎提示词语义忠实移植上游 prompts（中英双语能力保留），但载体从 Markdown 工作流改写为代码内结构化定义
- 默认界面语言中性（英文 CLI 输出），中文市场包在后续 feature 中以 overlay 方式加入
- PDF 渲染依赖系统 Chromium 内核组件；若环境缺失则降级为 HTML 输出并明示

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-1** 新用户从安装到拿到第一份评估报告 ≤ 30 分钟（含档案初始化，不含阅读时间）
- **SC-2** 单个 JD 从提交到产出"评估+简历草稿+求职信草稿"三件套 ≤ 5 分钟（正常网络与密钥条件下）
- **SC-3** 草稿事实保真率 100%：抽检任意草稿中的事实性陈述，均可追溯到档案来源（自动化断言 + 人工抽检双重验证）
- **SC-4** 架构级合规：全代码库不存在网络发送类调用路径；"未经确认外发"在测试中不可构造
- **SC-5** 全部测试在离线环境（mock 提供方）下通过；CLI 五个子命令端到端演示成功
- **SC-6** 分发物检查通过：含上游 LICENSE 版权行与 NOTICE 文件
- **SC-7** 第三方可依据 CLI JSON 输出的稳定 schema 二次开发（schema 版本化文档存在）
